  - gets the current main-map cell from MapGenerator

  - sets currentCellID

  - sets local PlayerController.isInNestedArea = true
  - saves previousNestedAreaID
  - saves mainMapCellID
  - sets parentNestedAreaID

  - sets isInMainMap = false

  - sets PlayerStats.Instance.RegisteredInTurnManager = true
  - manually registers the player with TurnOrchestrator.RegisterCharacter
  - validates/logs turn registrations
  - calls TurnOrchestrator.TryUpdateTurnContext()
  - refreshes maps through UIController

  That is a lot of ownership in one method.

  Nested area within nested area uses EnterNestedAreaWithinNestedArea(Cell cellWithNestedArea):

  - deregisters characters in the previous nested area
  - updates parent/current nested IDs

  currentNestedArea.NestedAreaLevel == 0 ||

  Current Turn-Registration Flow

  The intended architecture is:

  TurnOrchestrator
  → ExplorationTurnManager or CombatTurnManager
  → BaseTurnManager registration/cycle logic

  BaseTurnManager owns the actual active turn data:

  - characterTurnDataDict
  - sortedCharacterList
  - currentTurnIndex
  - isPlayerTurn

  Registration in BaseTurnManager.RegisterCharacter is keyed by Character.IInteractableID. Duplicate IDs are rejected with a warning.

  Turn order is:

  Register characters
  → StartTurnCycle()
  → SortCharacters()
  → ExecuteNextTurn()
  → OnPlayerTurnStart() or OnNPCTurnExecute()
  → EndTurnForCharacter()
  → ExecuteNextTurn()
  → EndCycle()

  ExplorationTurnManager differs from combat mostly by:

  - no delay
  - skips characters not in PlayerStats.Instance.CurrentNestedArea
  - resets player move points
  - calls PlayerController.Instance.UpdateAdaptiveActionMenu()
  - restarts continuously after cycle end

  CombatTurnManager differs by:

  - respects GameManager.Instance.ActiveTurnManager
  - uses delay when the area is hostile
  - resets player AP and MP
  - updates turn order UI
  - invokes OnPlayerTurn
  - restarts while active and while a player exists in the registry

  The problem is not the base turn engine. The base engine is fairly coherent. The problem is how characters get into it.

  - TurnOrchestrator.RegisterCharacter

  - Monster.OnDeath
  - NPC.OnDeath

  The current source of truth for active participants is split:

  - TurnOrchestrator.allCharacters is a broad list of all registered characters known to the orchestrator.
  - ExplorationTurnManager.characterTurnDataDict is the active exploration list.
  - CombatTurnManager.characterTurnDataDict is the active combat list.
  - INestedArea.GetAllCharactersInArea() can reconstruct area occupants from cells.

  first-level nested entry does not call TurnOrchestrator.EnterNestedArea, that is likely what happens on ordinary entry.

  Current Combat Flow

  Combat appears to be inferred, not explicitly started.

  The flow is approximately:

  Player/NPC attacks
  → Character.PerformAttack(...)
  → target.IsHostile = true
  → target.Stance = Hostile
  → CurrentNestedArea.UpdateHostileAreaStatus()
  → TurnOrchestrator.TryUpdateTurnContext()
  → if CurrentContext == Exploration and area.IsHostileArea
  → SwitchToCombatMode()

  But there is a catch: TryUpdateTurnContext() only switches into combat if the current context is already Exploration.

  if (CurrentContext == TurnContext.Exploration && hasHostiles)
      SwitchToCombatMode();

  If normal entry leaves the orchestrator in MainMap, combat will not start through this path.

  Combatants are selected in SwitchToCombatMode() from TurnOrchestrator.allCharacters, filtered by:

  character.IsInNestedArea &&
  character.CurrentNestedArea == PlayerStats.Instance.CurrentNestedArea

  Then each is registered into CombatTurnManager.

  This means combatants are not chosen from a dedicated combat encounter list. They are chosen from all known characters in the current nested area.

  That is simple and probably appropriate for the project, but it depends on:

  - allCharacters being accurate
  - each character having correct IsInNestedArea
  - each character having correct CurrentNestedArea
  - the player being present in the same data model
  - IsHostileArea being recalculated at the right time

  Enemy turns call Character.ExecuteTurnActions(). That resets AP, ensures state machine exists, switches hostile characters into HostileState, updates the state machine, then runs movement toward cells of
  interest.

  Player combat turns are started by CombatTurnManager.OnPlayerTurnStart():

  - updates turn order UI
  - resets player AP
  - resets player MP
  - updates adaptive action menu
  - invokes OnPlayerTurn

  Player combat actions usually come from adaptive action buttons in PlayerController. Button clicks execute interactions and call turnOrchestrator.PlayerTurnCompleted() when AP is exhausted or a pending
  action consumes the turn.

  Combat ends only when:

  area.IsHostileArea becomes false
  → TurnOrchestrator.TryUpdateTurnContext()
  → SwitchToExplorationMode()

  I did not find a strong explicit “combat ended now, clean up combat state” flow. Death methods deregister some entities and mark inactive, but hostile-area status updates are inconsistent after death/
  removal.

  Risk Register

  Definite problems:

  - TurnOrchestrator scene references for combatManager and explorationTurnManager are missing in SampleScene.
  - Normal first-level nested entry does not call TurnOrchestrator.EnterNestedArea, so CurrentContext likely remains MainMap.
  - When CurrentContext is MainMap, TurnOrchestrator.RegisterCharacter does not register into a concrete turn manager.
  - Combat transition only triggers from Exploration, not from MainMap.
  - Monster registers itself with TurnOrchestrator in its constructor, before placement/location may be valid.
  - Turn registration decisions are scattered across managers, entities, and nested areas.
  - Player location state is duplicated across several objects.
  - PlayerStats calls back into PlayerController for area transitions, which reverses expected ownership.

  Likely problems:

  - Deregistration is not consistently paired with every placement path.
  - BaseNestedArea.HandlePlayerExit() deregisters NPCs/animals but not monsters via its private DeregisterAllCharacters() implementation.
  - Death/removal may leave IsHostileArea stale unless something later calls UpdateHostileAreaStatus.
  - TurnOrchestrator.allCharacters can retain stale inactive characters if deregistration is missed.
  - PlayerStats.InCombat appears separate from TurnOrchestrator.CurrentContext; it may not reliably reflect actual combat context.
  - GameManager.ActiveTurnManager, PlayerStats.RegisteredInTurnManager, PlayerStats.InCombat, Character.InCombat, and TurnOrchestrator.CurrentContext are overlapping state flags.

  Possible concerns:

  - LeaveNestedAreaToParent() uses FacingCellParentID and FacingCellCoordinates; if facing-cell state is stale, parent exit can target the wrong area.
  - MapGenerator.FindNestedAreaBasedOnNestedAreaID() depends on nestedAreas being complete and free of duplicate IDs.
  - GetAllCharactersInArea() depends on characters being placed into the expected cell collections.
  - Animals are stored in cell.Animals, while NPCs/monsters are often stored in cell.Objects; rendering and registration paths may treat those differently.
  - BaseTurnManager.ValidateCharacterNestedAreas() and overrides can “correct” character area data, which may hide the original source of bad registration.

  Things that look okay:

  - BaseTurnManager duplicate registration protection by IInteractableID is useful.
  - BaseTurnManager adjusts currentTurnIndex when removing registered characters.
  - ExplorationTurnManager and CombatTurnManager both skip inactive/wrong-area characters.
  - AreaEntryCoordinator is a good direction: it removes some population responsibility from PlayerController.
  - MapDisplayUI reads from PlayerStats.CurrentNestedArea and can display nested areas independently of turn registration.

  Recommended Target Architecture

  For this project, I would keep the architecture Unity-friendly and avoid a large framework.

  The ideal shape:

  PlayerController
  → requests movement / area transition

  AreaEntryCoordinator or AreaTransitionService
  → owns enter/exit nested area flow
  → updates PlayerLocationState / PlayerStats
  → asks population managers to place entities
  → calls TurnOrchestrator.EnterNestedArea / EnterMainMap
  → tells UI to refresh

  TurnOrchestrator
  → only public route for turn registration/context switching
  → owns Exploration vs Combat context
  → owns combat transition checks

  ExplorationTurnManager
  → owns exploration participants only

  CombatTurnManager
  → owns combat participants only

  NestedArea
  → owns area map and contained entities
  → does not directly decide turn registration except through clear lifecycle calls

  Yes, nested-area entry/exit should be centralized into one coordinator.

  Yes, TurnOrchestrator should be the only public route into turn registration. Managers can still call it, but they should not decide context.

  Yes, CombatTurnManager should own combatants separately from exploration participants.

  Yes, PlayerController should stop directly managing area transitions and turn registration over time.

  Entities should generally not subscribe themselves in constructors. Area/combat managers should register them after placement.

  Current location should probably remain visible through PlayerStats, but the write authority should be centralized. A small PlayerLocationState or AreaTransitionCoordinator would be cleaner than letting
  every system mutate PlayerStats.

  UI can remain direct-call for now for major refreshes. Events would help later for OnAreaEntered, OnAreaExited, OnCombatStarted, OnCombatEnded, but converting everything to events immediately would be
  overengineering.

  Direct Answers

  1. Is nested-area entry/exit currently understandable?
     Understandable after tracing, but not locally obvious.

  2. Is it robust?
     No. It works visually, but state ownership and turn context are fragile.

  3. Is there a single source of truth for where the player is?
     No. PlayerController is the practical writer, PlayerStats is the global mirror, and CurrentPlayerCharacter also stores location.

  4. Is turn registration centralized enough?
     No. Calls route through TurnOrchestrator, but registration decisions are scattered.

  5. Is deregistration safe enough?
     Not yet. Duplicate protection exists, but missed deregistration and stale global lists remain likely.

  6. Is combat cleanly separated from exploration?
     Partially in manager classes, but not cleanly in state flow. Combat depends on hostile-area polling and shared registrations.

  7. What is the most dangerous part of the current design?
     Normal nested entry bypasses TurnOrchestrator.EnterNestedArea, so the orchestrator context can remain MainMap while the player is inside a nested area.

  8. What is the safest first improvement?
     Add TurnOrchestrator diagnostics and auto-resolve missing manager refs without changing gameplay flow.

  9. What should absolutely not be refactored yet?
     Do not rewrite Character, BaseNestedArea, or the full interaction system yet. Do not change serialized field names. Do not replace the turn system wholesale.

  10. If I inherited this project, what would I do first?
     I would document the intended state machine, add runtime diagnostics to prove actual context/registration state, then make TurnOrchestrator safely resolve its managers before touching behavior.
