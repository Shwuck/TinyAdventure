  1. Executive Summary

  The current turn lifecycle is salvageable but not reliable enough yet for a game where turn state is foundational.

  The core turn engine, /C:/Game Design/Unity/TinyAdventure/Assets/BaseTurnManager.cs, is reasonably coherent: it has a registry, duplicate checks, sorted turn order, player-turn waiting, NPC execution, and
  cycle restart behavior. The fragile part is the lifecycle around it: entering areas, leaving areas, placing entities, death/removal, and combat transitions.

  The most serious issue is architectural desynchronisation:

  Player visually enters nested area
  but TurnOrchestrator may still be in MainMap context
  and registration may only touch allCharacters, not the active manager.

  The intended design appears to be:

  TurnOrchestrator
  → ExplorationTurnManager
  → CombatTurnManager

  But the current practical flow is:

  PlayerController / NPCManager / AnimalManager / MonsterManager / BaseNestedArea / Character
  → direct TurnOrchestrator.RegisterCharacter / DeregisterCharacter calls

  So registration goes through the orchestrator, but the decision of when registration should happen is scattered.

  The system is currently:

  - understandable after tracing,
  - duplicated in responsibility,
  - fragile around entry/exit and combat transition,
  - overcomplicated mostly because ownership is unclear,
  - still very much recoverable with diagnostics and small policy changes.

  2. Current Turn-State Model

  The current contexts are defined in /C:/Game Design/Unity/TinyAdventure/Assets/TurnOrchestrator.cs:

  MainMap
  Exploration
  Combat

  MainMap means turn logic is effectively disabled. TurnOrchestrator.RegisterCharacter() adds to allCharacters, but does not route to a turn manager.

  Exploration means ExplorationTurnManager should contain active turn participants for the current nested area.

  Combat means CombatTurnManager should contain active combatants for the current combat situation.

  Exploration behavior:

  - ExplorationTurnManager.OnPlayerTurnStart() resets player MP.
  - NPCs execute automatically through npc.ExecuteTurnActions().
  - OnCycleEnded() immediately restarts the cycle.
  - It is intended to feel continuous.

  Combat behavior:

  - CombatTurnManager.OnPlayerTurnStart() resets AP and MP.
  - Player turn waits until TurnOrchestrator.PlayerTurnCompleted().
  - NPC turns execute automatically.
  - Turn order UI is updated.
  - Combat cycle restarts while active and while a player exists.

  The distinction exists in code, but the transition into those contexts is not yet reliable.

  4. Exploration Registration Policy

  Exploration registration should begin only after a nested-area transition has fully succeeded.

  Recommended policy:

  - Area entry should register all current-area occupants in one batch.
  - The player should be explicitly registered first.
  - The participant list should be rebuilt from the current area’s actual occupants.
  - Generated-but-not-placed entities should never register.
  - Dead, inactive, despawned, removed, or expired entities should never register.
  - Previous-area entities may remain in persistent world data, but not in the active exploration manager.
  - Repeated entry should rebuild or validate the list idempotently.
  - NPCs/animals/monsters should not self-register.
  - If no NPCs/animals/monsters exist, exploration should still register the player or run a lightweight player/world turn mode.

  The exploration entry policy should be:

  Complete area transition
  → set player location state
  → populate/restore area
  → collect active occupants from area
  → clear exploration manager
  → register player first
  → register active occupants
  → set context Exploration
  → start/continue exploration cycle

  Exploration should feel continuous. The player should not need combat-style AP decisions for every world tick unless the design explicitly wants that.

  5. Combat Registration Policy

  Combat should be stricter than exploration.

  Recommended policy:

  - Combat should start through an explicit orchestrator method, even if the trigger is inferred.
  - Hostile-area status can be the trigger, but transition should be explicit:

  TurnOrchestrator.BeginCombat(activeArea, cause)

  Combatants should be selected by policy, not by accident.

  Good default combatant policy:

  - always include the player,
  - include active hostile entities in the current area,
  - include active allies already engaged,
  - include neutral bystanders only if design says they participate,
  - exclude dead/inactive/despawned/generated-unplaced entities,
  - exclude previous-area entities,
  - exclude current-area noncombatants unless they are intentionally part of combat.

  CombatTurnManager should own a separate combatant list. It may be rebuilt from current area occupants or copied from exploration participants, but rebuilding from authoritative area occupants is safer.

  Combat start should:

  Pause or clear exploration active turns
  → build combatant list
  → clear combat manager
  → register player
  → register combatants
  → reset AP/MP at turn start only
  → start combat cycle

  Combat end should:

  detect no active hostiles / player dead / flee / scripted end
  → clear combat manager
  → clear combat flags on survivors
  → rebuild exploration participant list from current area
  → resume exploration

  Combat should not be treated as faster exploration. It has its own stricter participant set and player input gating.

  6. Deregistration Policy

  Deregistration should be idempotent.

  Rules:

  - Leaving an area: deregister all active occupants from active managers in one batch.
  - Entering a different nested area: deregister old active area, update location state, register new active area.
  - Returning to parent area: rebuild from parent occupants.
  - Returning to main map: clear exploration and combat managers; clear active context to MainMap.
  - Death: immediately remove from all active turn managers and mark inactive/dead.
  - Despawn/removal/expiry: immediately remove from active turn managers.
  - Inactivity: should prevent turns immediately; cleanup pass should remove the entity.
  - Combat ending: clear combat manager completely, then rebuild exploration.
  - Player death: suspend/clear active turn managers.
  - Scene reload/reset: clear all registries.
  - Failed entry/generation: do not change context or registration if transition did not complete.

  When should an entity remain in allCharacters?

  - Only if allCharacters is intentionally “current area known participants.”
  - If it is meant to be active-session registry, remove inactive/left/dead entities.
  - If it is meant to be persistent world registry, rename/rethink it later. Right now it behaves like active lifecycle state, so stale entries are dangerous.

  8. Registration And Deregistration Invariants

  Global invariants:

  - If context is MainMap, no exploration or combat participants should be active.
  - If the player is visually in a nested area, context should not be MainMap.
  - TurnOrchestrator.allCharacters should agree with the active area policy.
  - No manager should contain duplicate IInteractableID.
  - Missing manager refs should be diagnosed before first registration.

  Exploration invariants:

  - ExplorationTurnManager contains only active, alive, placed entities in the current nested area.
  - Player is registered when exploration is active.
  - Previous-area entities do not take exploration turns.
  - Generated-but-unplaced entities are absent.
  - Exploration can run with only the player.

  Combat invariants:

  - CombatTurnManager contains only active combatants.
  - Player is registered in combat unless dead.
  - Combat manager is empty after combat ends.
  - Exploration manager is paused or inactive during combat.
  - Dead/inactive combatants are removed before the next turn.

  Area-entry invariants:

  - Area exists.
  - Area map exists.
  - Player position is valid.
  - PlayerStats, PlayerController, and CurrentPlayerCharacter agree.
  - Entity position, cell membership, CurrentNestedArea, and IsInNestedArea are correct before registration.

  Area-exit invariants:

  - Active managers are cleared or rebuilt.
  - Player nested data is cleared or transferred.
  - Old area entities do not keep taking turns.
  - Main map context has no nested turn participants.

  Death/removal invariants:

  - Dead entity does not receive turns.
  - Inactive entity does not receive turns.
  - Removed entity is not in cell occupant list and not in active turn manager.
  - Hostile-area status is recalculated after death/removal.

  13. Final Summary

  Top 10 desynchronisation risks:

  1. Nested entry does not switch orchestrator to Exploration.
  2. TurnOrchestrator manager refs are missing in scene YAML.
  3. Registering while context is MainMap only updates allCharacters.
  4. Monster constructor registration before placement.
  5. Death/removal not consistently ending combat or recalculating hostile status.
  6. Previous-area entities remaining active.
  7. Generated-but-unplaced entities becoming registered.
  8. PlayerController/PlayerStats/CurrentPlayerCharacter disagreeing on area.
  9. Combat manager retaining stale combatants after combat.
  10. Exploration manager missing active current-area occupants.

  Top 5 diagnostics:

  1. Orchestrator manager-ref check on Awake.
  2. Context/location audit after every area transition.
  3. Area occupant count versus active manager count.
  4. Dead/inactive/wrong-area registered audit before turn cycle.
  5. Combatant/hostile status audit after every death/removal.

  Top 5 invariants:

  1. Player visually in nested area implies context is Exploration or Combat.
  2. ExplorationTurnManager only contains active current-area occupants.
  3. CombatTurnManager only contains active combatants.
  4. Dead/inactive/unplaced entities never receive turns.
  5. Leaving an area clears or rebuilds active participants.

  Recommended exploration policy: after a successful nested-area entry, rebuild exploration participants from the authoritative current area, register the player first, register only active placed occupants,
  ignore generated/unplaced/dead/inactive entities, and allow exploration to continue even if the player is alone.

  Recommended combat policy: combat should start through an explicit orchestrator method, even if triggered by hostile-area status. Combat should clear or pause exploration, build a strict combatant list,
  always include the player if alive, include active hostiles/engaged allies by policy, reset AP/MP on turns, wait for player action, and end by clearing combat and rebuilding exploration.

  Recommended deregistration policy: deregistration should be idempotent and centralized. Area exit, death, despawn, expiry, inactivity, combat end, player death, and failed transitions should all remove
  affected entities from active managers safely, then validate counts and context.

  Safest first patch batch later: add TurnOrchestrator manager-reference diagnostics/auto-resolution, add context/participant summaries, and add an area-entry audit. Do not alter behavior until those logs
  prove the current state.

  Golden rule: An entity may only receive turns if the TurnOrchestrator can prove it is active, alive, placed in the current active area, registered in exactly one appropriate active manager, and valid for the
  current context.
